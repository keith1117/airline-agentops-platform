# P3/P4 Bounded AgentOps Implementation Record

[English](P3-P4.md) | [中文](<P3-P4(Chinese).md>)

> **Status:** P0–P4 development is complete. This document is retained as the design rationale, implementation history, and acceptance record for the bounded AgentOps phases.

## Summary

The project already had the core elements of a real AI Agent application: an LLM/native tool-calling adapter, JSON router, RAG, memory, tools, traces, evaluation, and Docker. Before P3, however, its runtime was primarily **single-step routing plus backend workflows**, rather than a complete observation-driven, multi-step Agent loop.

The next stage was divided into two layers:

- **P3: Bounded Autonomous ReAct Agent**  
  Upgrade the single-step Agent into a controlled multi-step loop: `plan/action → tool execution → observation → next action/final`, constrained by maximum steps, tool permissions, and transaction-confirmation boundaries.
- **P4: AgentOps Governance, Evaluation, and Human-in-the-loop**  
  Once P3 was stable, add governance, evaluation, observability, and a human-confirmation queue so the project operates like an enterprise Agent platform instead of simply accumulating features.

The default strategy was to avoid an infinite autonomous agent. Airline booking involves purchases, cancellations, refunds, and authorization, so the intended final design is bounded autonomous multi-step execution.

## P3 Key Changes

### P3.1 Bounded ReAct Booking Preparation

The first implementation focused on one stable vertical slice instead of rewriting every Agent flow at once.

Runtime modes introduced:

```env
AGENT_RUNTIME_MODE=single_step | bounded_react
MAX_AGENT_STEPS=4
```

The initial default remained:

```env
AGENT_RUNTIME_MODE=single_step
```

`bounded_react` was first enabled explicitly and later became eligible for automatic selection after stabilization.

First supported scenario:

```text
Find the cheapest United flight from SFO to LAX next month and prepare a booking.
```

Target execution chain:

```text
User goal
-> select search_flights
-> observe available flights
-> rank/select cheapest valid flight
-> stop with booking_search_ready
-> display a Book handoff button
-> user continues on the Search Flights page
-> user manually reviews the exact flight and enters payment details
```

Implementation boundaries:

- The LLM/native router selects the next action but never executes SQL or transactions directly.
- The backend continues to execute tools, enforce permissions, and format business results through the tool registry.
- Customer Agent does not create or confirm a purchase inside chat; it can display bookable flights and hand off to Search Flights.
- `create_booking_intent` and `confirm_booking` are excluded from the customer chat loop. The user must submit payment information manually on Search Flights.
- `cancel_customer_ticket` is not part of the P3.1 loop and remains behind its existing path.
- Full chain-of-thought is not stored. Trace fields use `decision_summary`, `action`, `observation`, and `stop_reason`.

Core implementation locations:

- `agent_service/config.py`: adds `AGENT_RUNTIME_MODE`.
- `agent_service/react_agent.py` or `agent_service/bounded_runtime.py`: implements the bounded loop.
- `agent_service/tool_registry.py`: adds tool-risk classification.

Tool-risk categories:

```text
safe_read:
  search_flights
  get_customer_trips
  get_customer_ticket
  get_user_preferences
  answer_policy_question
  staff analytics tools

controlled_write:
  remember_user_preference

human_confirmed:
  cancel_customer_ticket
```

### P3.2 Cancellation Preview Flow

After P3.1 stabilization, the bounded runtime was extended to cancellation while preserving the confirmation boundary.

Target flow:

```text
User asks to cancel flight
-> ask for ticket_id if missing
-> get_customer_ticket
-> calculate refund preview
-> stop with cancellation_confirmation_required
-> user confirms through separate confirmation action
```

Requirements:

- The Agent may explain cancellation fees and estimated refunds.
- Ordinary chat cannot cancel a ticket directly.
- Refund rules for `ON_TIME`, `DELAYED`, and `CANCELLED` remain backend-owned and cannot be invented by the LLM.

### P3.3 Staff Multi-step Copilot

Staff multi-step analysis followed customer-flow stabilization.

Example:

```text
Which route has strong sales but poor reviews?
```

Target flow:

```text
get_route_performance
-> analyze_reviews
-> combine observations
-> final recommendation
```

Requirements:

- Staff-only tools can be called only with the staff role.
- Customers can never enter staff analytics tools.
- The LLM may summarize the final analysis, but all data must come from backend tool observations.

### P3.4 Optional Runtime Auto Mode

Added:

```env
AGENT_RUNTIME_MODE=auto
```

Semantics:

- Simple requests continue through single-step routing.
- Requests requiring multiple coordinated tools use bounded ReAct.
- Explicit `single_step` and `bounded_react` modes remain available for demonstrations and tests if automatic classification becomes unstable.

### P3 Completion Status

All planned P3.1, P3.2, P3.3, and P3.4 capabilities were implemented:

- Customer booking preparation uses bounded search, observation, and selection, then hands off to Search Flights checkout.
- Cancellation uses preview plus explicit confirmation; ordinary chat never cancels directly.
- Staff Copilot supports a route-performance plus review-analysis multi-tool chain.
- `auto` runtime can select between single-step and bounded ReAct.
- Focused tests cover step limits, tool risk, role permissions, trajectories, and stop reasons.

Current status: **P4 implementation complete**. P4.1 evaluation, P4.2 AgentOps dashboard, P4.3 persistent human-confirmation queue, P4.4 governance hardening, and cross-timezone governance are implemented. Offline deterministic regression passes, and the Docker MySQL acceptance command remains available for environments with Docker daemon access.

## P4 Key Changes

P4 began after P3 passed rather than competing with P3 implementation time.

### Agent Eval Upgrade

The existing eval was extended with:

- Multi-step task success rate.
- Tool-sequence accuracy.
- Unauthorized-call rejection rate.
- Confirmation-gate hit rate.
- RAG citation rate.
- Fallback rate.
- Failed trace case list.

Bounded ReAct eval cases added:

```text
Search -> booking_search_ready handoff
Search no result -> no booking handoff
Cancel request missing ticket -> clarification
Cancel preview -> no direct cancellation
Staff route + review analysis -> combined answer
Customer staff-tool request -> denied
```

#### P4.1 Completion Status

The Agent Eval Upgrade was completed:

- Added multi-step task success, tool-sequence accuracy, unauthorized rejection, confirmation-gate hit rate, fallback rate, and metric denominators.
- Failed cases include execution metadata, failure type, and bounded trajectories to identify the exact failing step.
- P4 cases use a read-only dynamic future-ticket fixture so cancellation-preview tests do not expire with fixed ticket numbers or dates.
- Docker MySQL P4 eval: `6/6 passed`; multi-step, tool order, unauthorized rejection, and confirmation gate were all `1.0`.
- Full Docker MySQL regression at that milestone: `100 passed`.

### AgentOps Dashboard / Trace Viewer

Existing traces, metrics, and trajectories were surfaced through a clearer debugging view containing:

- `request_path`
- `runtime_mode_used`
- `router_used`
- `tools_used`
- `step_count`
- `stop_reason`
- `fallback_reason`
- `latency`
- `confirmation_required`

The initial design intentionally allowed a simple HTML/debug page without requiring a complex frontend.

#### P4.2 Completion Status

The AgentOps Dashboard and Trace Viewer were completed:

- FastAPI exposes a read-only dashboard aggregation endpoint that filters recent Agent traces by role, request path, runtime mode, and outcome.
- The staff-only `/staff/agentops` page shows trace count, average latency, average steps, fallback rate, errors, and confirmation gates.
- The dashboard also displays current Agent-service endpoint metrics, tool-call count, and average latency.
- The trace viewer shows request path, runtime, router, tools, step count, stop reason, fallback/error details, and bounded trajectories.
- Views expose short decision/action/observation metadata without raw reasoning or full chain-of-thought.
- Desktop, 390px mobile layout, filters, and staff-only access were verified; full Docker MySQL regression at that milestone: `106 passed`.

### P4.3 Human-in-the-loop Queue

A demonstration-oriented human-confirmation view was added for:

- Pending booking handoffs / checkout starts.
- Pending cancellation previews.
- Confirmed / rejected actions.
- Audit trail.

Principles:

- The LLM may recommend an action.
- High-risk actions execute only after explicit customer or staff confirmation; purchases must be completed through Search Flights checkout.

#### P4.3 Completion Status

- Implemented persistent booking handoffs, checkout starts, cancellation previews, confirmed/rejected/expired/failed states, and per-item audit history.
- Customer Pending Actions can operate only on the customer's own actions; Staff Action Queue can view only records for the staff member's airline and cannot confirm transactions for customers.
- Purchases must enter Search Flights checkout first. Payment submission locks action, flight, and ticket-ID allocator rows; repeated submissions return the same ticket number and the last seat cannot be oversold.
- Cancellation confirmation is bound to its original preview. Execution stops if refund conditions change or the preview expires. Transaction results and audit records commit together.
- Payment stores only `MOCK-PAYMENT`, never the card number entered by the user.
- Offline regression: `90 passed, 23 skipped`; Docker MySQL full regression at that milestone: `113 passed`.

### P4.4 Governance / Safety Hardening

Enterprise Agent boundaries were documented and implemented:

- Tool-risk categories.
- Role-based tool permissions.
- Transaction guardrails.
- Audit log.
- Unsupported-request refusal.
- No direct SQL from the LLM.
- No real payment or real airline inventory.

#### P4.4 Completion Status

- FastAPI `/api/*` requests require a short-lived signed service identity and enforce customer, staff, and operator scopes, including airline isolation for dashboards.
- Flask sessions use a persistent secret with restrictive permissions, secure cookie flags, and session-bound CSRF tokens on every state-changing form.
- High-risk model tools are blocked from direct registry execution. HTTP booking confirmation is retired with `410 Gone`; purchases remain a user-driven checkout flow.
- Trace and dashboard responses redact customer content from staff views while retaining operational metadata and auditability.
- Pydantic request bounds, eval-suite validation, and controlled action errors provide explicit failure behavior at service boundaries.

### P4.5 Final Product Polish

- Customer flight search accepts IATA codes and supported English or Chinese city names for the complete 24-airport synthetic catalog, including legacy `BEI`/`PEK` and `HKG`/`HKA` variants.
- The search tool can match city names directly against the `Airport` table, so routed tool calls are no longer limited to IATA-only input.
- Chinese relative periods `下个月`, `今年`, and `明年` preserve the same date-window behavior as their English equivalents.
- Customer Agent and Staff Copilot use one full-width conversation panel. Wide result tables scroll within their message cards, and development-oriented Demo prompts panels were removed.
- Final verification: local regression `113 passed, 24 skipped`; Docker MySQL full regression `138 passed`; Playwright confirmed that Chinese `旧金山` to `洛杉矶` returns `SFO` to `LAX` inventory and that both Agent pages render without Demo prompts.

### Time Governance and Dynamic User Timezone

The system uses consistent internal time semantics while supporting users across timezones instead of fixing the application to the developer's location.

Target design:

```text
Backend / MySQL canonical time
-> store and compare timestamps in UTC
-> detect or accept the user's IANA timezone
-> convert timestamps only for display and user-entered local dates
```

Requirements:

- Backend services, the Agent service, Docker, and MySQL use UTC internally.
- Database storage and comparisons use timezone-aware UTC timestamps, replacing assumptions based on naive `datetime.now()` or `date.today()` calls.
- The frontend detects the current IANA timezone, such as `America/New_York` or `Asia/Shanghai`, and allows users to override it.
- Flight times preserve the local timezone semantics of the departure and arrival airports rather than treating airport-local time as the user's current timezone.
- `this month`, `this year`, and report boundaries explicitly use the configured business timezone instead of changing with the developer machine.
- Traces and audit logs use UTC; user pages convert displayed values and label the timezone.
- Every Docker service starts with a consistent, verifiable timezone configuration.

#### Time Governance Completion Status

- MySQL sessions, Python services, Docker containers, trace export, and action-audit timestamps use UTC; `/health` reports both Python and MySQL clocks.
- Flight input accepts airport-local wall times, rejects DST gaps and unresolved ambiguous times, and displays airport and traveler zones separately.
- Browser timezone detection plus `/preferences/timezone` supports a persisted IANA override; date searches and reports use DST-aware UTC bounds.
- `this month`, `this year`, and custom report ranges are anchored to `BUSINESS_TIMEZONE`, independent of the host machine timezone.
- P4 security/timezone tests pass in the local deterministic suite; MySQL transaction and clock tests remain enabled in the Docker acceptance command.

## Test Plan

P3.1 first had to pass:

- Existing P0/P1/P2 tests do not regress in `single_step` mode.
- In `bounded_react` mode, booking preparation calls at least `search_flights` and returns `booking_search_ready`.
- No booking handoff or booking intent is produced when no bookable flight exists.
- `MAX_AGENT_STEPS` prevents unbounded loops.
- `create_booking_intent` and `confirm_booking` cannot execute from the customer chat loop.
- `cancel_customer_ticket` is rejected or converted to clarification in the P3.1 bounded loop.
- Customers cannot call staff tools.
- Traces include `decision_summary`, `action`, `observation`, and `stop_reason`, without full chain-of-thought.
- Native, JSON, and deterministic-router fallbacks remain available.
- The full Docker MySQL test suite continues to pass.

P3.2 also had to cover:

- Missing ticket → clarification.
- Ticket found → refund preview.
- Correct `ON_TIME` / `DELAYED` refund-fee rules.
- Cancellation preview does not directly modify ticket status.
- Only a confirmed action performs the real cancellation.

P3.3 also had to cover:

- Correct staff multi-tool sequence.
- Staff answers grounded only in tool observations.
- Rejection of unauthorized customer requests.

P4 also had to cover:

- Eval reports emit summary metrics.
- Trace viewer displays bounded ReAct steps.
- Human-in-the-loop queue lists pending actions.
- UTC storage and cross-timezone presentation pass tests, with consistent Python, MySQL, and Docker time boundaries.
- `this month` and `this year` reports do not drift with user travel or container timezone changes under the configured business timezone.
- Departure and arrival times convert correctly for airport-local and user-display timezones.
- README serves as project documentation without interview-oriented language.

## Assumptions

- P3.1/P3.2/P3.3/P3.4 are the implemented P3 vertical slices; any later P3 work should continue in small, verified increments.
- P3 targets bounded autonomous multi-step execution rather than an infinite autonomous agent.
- P3 can retain `single_step` as the default, with `auto` as an explicit option to avoid demo behavior drift.
- LLM/native tool calling selects tools and structures responses; backend tools still own business execution.
- Customer Agent does not purchase tickets. Purchases occur only after the user reviews the flight and submits payment information on Search Flights.
- High-risk actions such as `cancel_customer_ticket` must remain confirmation-gated.
- Real payment, real airline APIs, real SFT, and real Agentic RL are out of scope.
- P4 begins only after P3 is stable and its tests pass.
